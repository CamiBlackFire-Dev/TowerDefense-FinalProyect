# TowerDefensive-FinalProyect

Unity 6 tower-defense game (3D, URP). No CI or README yet; Unity EditMode tests live under `Assets/_Custom/Tests/Editor/`.

## Stack (verified in ProjectSettings/Packages)
- Unity **6000.3.19f1**, URP **17.3.0** (Gamma color space), ProBuilder 6.1.2 (level geometry), Recorder 5.1.7
- **New Input System only** (`activeInputHandler: 1`): legacy `UnityEngine.Input` is disabled — use `UnityEngine.InputSystem` / PlayerInput components
- MCPForUnity (`com.coplaydev.unity-mcp`, git package) is installed: the unityMCP tools drive the editor, but only work while the Unity Editor is open with the bridge running
- No `.asmdef` files — default compilation

## Layout
- All game content lives in `Assets/_Custom/` (`Scenes/`, `Scripts/`, `Prefabs/`, `Models/`, `Materials/`); URP pipeline assets live in `Assets/URP/`. Keep new content inside `_Custom/`, never at Assets root.
- Only scene: `Assets/_Custom/Scenes/0_Main.unity` (also the only scene in Build Settings). Contains Ground, Main Camera, Directional Light, Global Volume and the persistent `Board` object (named `Board 2048`).
- `Assets/_Custom/Scripts/` contains the board model/view (`BoardGrid`, `BoardManager`, `Tower`), input (`InputController`), economy (`EconomyManager`) and shop (`TowerShop`); `Assets/_Custom/Data/Towers/` holds the balance ScriptableObjects (`TowerLevel1..4.asset` + `TowerCatalog.asset`); `Assets/_Custom/Materials/` contains `CellMaterial.mat`; `Assets/_Custom/Models/Kenney Assets/Tower Defense/` holds the imported FBX models (tiles, towers, enemies, details). `Prefabs/` remains empty.

## Gotchas
- No CLI build/test/lint — verification happens in the Unity Editor: watch the Console for compile errors after script changes, then test in Play mode.
- `.meta` files are versioned (see .gitignore) and must never be deleted or recreated — they hold the GUIDs that scene/prefab references depend on. Create/move/rename assets only through the Unity editor (or MCP), never by hand.
- Script class name must match its file name; use URP-compatible shaders (e.g. `URP/Lit`), not Built-in RP shaders.
- Don't hand-edit scene/prefab `.unity`/`.prefab` YAML when an editor/MCP operation (or a C# script) can do the job.
- `BoardManager` uses `ExecuteAlways`: its editable scene children live under `Board/Cells` (16 cells) and `Board/Towers`. Use its custom Inspector to change levels and rebuild the view; do not recreate those children manually.
- Enemy/combat layer (merged from teammates, kept where they wrote it): `Assets/JeanAssets/Scripts/` has `Path` (waypoint list + gizmo), `TestEnemyMovement` (walks the waypoints, `ApplySlow` for the drone EMP) and `Tower/TowerTargetDetector` (OverlapSphere on the **Enemy** layer, picks the closest, aims the tower). `Assets/Enemies/RutaEnemigo.cs` is an older NavMesh experiment — **not used**, the fixed path is waypoint-based. Only add to those files, never rewrite them; the additions so far are `Path.SetWaypoints`, `TestEnemyMovement.SetPath`/`Finished` and `TowerTargetDetector.CurrentTarget`/`SetDetectionRange`/`SetEnemyLayer`.
- `PathBuilder` (`ExecuteAlways`, child of `Board 2048`) generates the enemy road: a squared **C** around the board — `BuildPathPoints()` is pure math (16 tiles for a 4x4 board, ring at `boardCells*tileSize/2 + tileSize/2`), then it creates `Tiles/` (mesh normalized to `tileSize`, top face at `surfaceY`, BoxCollider on the **Floor** layer for the drone bomb) and `Waypoints/`, and feeds them to `Path`. Tile rotation is a guess from the walking direction plus a per-type yaw offset in the Inspector — the waypoints (i.e. the movement) never depend on that guess.
- Enemy assets are **generated, never hand-made**: the menu `Tower Defense > Crear prefabs de enemigos` (`EnemyPrefabBuilder`) turns every loose model in `Models/Enemies/` (skipping `Rig_*` and the `Props & weapons/` subfolder) into a prefab in `Prefabs/Enemies/` with the Enemy layer, a CapsuleCollider measured from the real bounds, `TestEnemyMovement` + `EnemyFacing` + `EnemyHealth` and the Animator, then wires the scene's `EnemySpawner` and the `PathBuilder` waypoint height. Re-run it after adding a model instead of editing prefabs by hand. `Assets/Enemies/` (Johan's old NavMesh test) contains **no** enemy assets — don't look for them there.
- `EnemyAnimatorBuilder` builds `Animations/EnemyAnimator.controller` from the clips inside `Rig_Medium_MovementBasic` (`Walking_A/B/C`, `Running_A/B`) and `Rig_Medium_General` (`Death_A/B`, `Hit_A/B`, `Idle_A/B`, `Spawn_Ground`...): two states, `Walk` (default, and the tool forces `loopTime` on that clip via `ModelImporter`) and `Death`, reached from Any State by the **`Die`** trigger — the same string as `EnemyHealth.dieTrigger`. The Animator lives on the model child (that's where the bones are) with `applyRootMotion = false`, because the movement belongs to `TestEnemyMovement`. Before touching clips, `EnsureController()` calls `ShareAvatarAcrossRigs()`: the `Rig_*` FBX files carry no mesh, so Unity can't build a humanoid avatar for them on its own (they import with `avatarSetup: NoAvatar`) — the tool points every `Rig_*` at `Skeleton_Warrior`'s avatar (`ModelImporter.avatarSetup = CopyFromOther` + `sourceAvatar`) and reimports, skipping any rig already pointed there by hand. If a new `Rig_*` is added, re-running the menu wires it automatically.
- `EnemyHealth.Die()` pays the reward, **disables the movement and every collider** (so towers stop shooting a corpse), fires the death animation and destroys the object after `deathDelay`. Keep that order if you touch it.
- `EnemySpawner` prepares each enemy it creates (`SetPath`, `EnemyHealth.Setup`, destroy on `Finished`), so `TestEnemy.prefab` needs no scene references. `TowerAttack` reads damage/range/attackRate from `TowerCatalog` by `Tower.Level` (this is what finally wires the ScriptableObjects in `Data/Towers/`), pushes the range and the Enemy layer into `TowerTargetDetector`, and calls `EnemyHealth.TakeDamage`. Merging towers therefore upgrades their firepower for free.
- Buy tower flow is `InputController.BuyRequested` (key **B**, temporary until UI) → `TowerShop.TryBuyTower()` → `EconomyManager.TrySpend()` → `BoardManager.PlaceTowerRandom(1)`. Buying is blocked (no money spent) when the board has no free cells.
- `BoardGrid.Move()` returns a `MoveResult` with `TowerMoveEvent`/`TowerMergeEvent` lists (deterministic, used to animate). In Play Mode `BoardManager` animates slides and merge pulses via coroutines (no external tweening); **moves pressed during an animation are buffered (FIFO, `maxBufferedMoves` default 8) instead of ignored**, and the next move starts as soon as the slide ends — the merge pulse continues in parallel and never blocks input. Outside Play Mode (EditMode tests) visuals update instantly.
- All the design knobs live in `BoardManager`'s **Visuales** header: `cellSize`/`cellThickness`, `cellMesh` + `cellMaterial` (the grid tile) and `towerLevelModels` (one model per level: `[0]` = level 1, `[1]` = level 2, …; the last entry is reused for higher levels). They are `public`, so they are drag & drop in the Inspector.
- Swapping `cellMesh` never changes the board size: `BoardManager.CreateCell` scales any mesh to the cell box (`cellSize * 0.9` × `cellThickness` × `cellSize * 0.9`), recenters it by its bounds and copies those bounds into the `BoxCollider`. Keep that normalization when touching cell creation.
- Tower visuals are plug-and-play: `Tower` is only the logical anchor (movement/level); `TowerVisual` owns model, scale, color, spawn growth and merge pulse. `BoardManager` calls `Tower.SetModel(...)` with the model of the level (on create, on edit-mode refresh and on merge) — `TowerVisual.SetModel` swaps the child, ignores repeated calls with the same prefab and falls back to a cube when the list is empty. `BoardManager` positions roots at the cell anchor; `TowerVisual` handles the model's height offset. Do not hand-scale or recolor tower roots; tune `baseScale`/`baseOffsetY` on `TowerVisual` instead.
- The tint per level is edited **only** in `BoardManager` → **Colores de las torres** (`useLevelColors` + `towerLevelColors`, same `[0]` = level 1 convention). `TowerVisual` does not serialize a palette: `BoardManager.ApplyTowerColors` pushes it with `SetLevelColors(...)` on create/refresh, and the tower falls back to `DefaultPalette()` only if used without a board. Do not re-add a palette field to `TowerVisual` — a per-tower copy that the board silently overwrites is what confused the designer before. `useLevelColors` off clears the property block, so the model's own material shows.
- `TowerVisual.modelBaseScale` (the model's imported scale) is captured **once** and serialized — it must never be re-derived from the already-scaled `Visual` child, or towers shrink every time Play Mode starts. `SetModel` re-captures it from the freshly instantiated prefab; for a model swapped by hand, right-click the `TowerVisual` and use *Restablecer escala base del modelo* (or rebuild the board view).

## Code style
- Comments in **Spanish**, always single-line with `//`. Never use `/// <summary>` XML docs.
- Write code readable by junior developers: descriptive names, short methods, obvious flow, no fancy patterns.
- **No namespaces** anywhere (not everyone on the team wraps their scripts, so the project stays on the global namespace).
- **No `#if UNITY_EDITOR` and no `using UnityEditor` in runtime scripts.** Everything editor-only lives in `Assets/_Custom/Scripts/Editor/` (e.g. `BoardManagerEditor` marks the scene dirty after rebuilding). Runtime code that must work in the editor uses `ExecuteAlways` + `Application.isPlaying`.
- Fields the designer tweaks are plain `public` fields with a `//` comment and grouped under a `[Header(...)]`; `[SerializeField] private` stays only for wiring that is not meant to be touched.
- Tests live in `Assets/_Custom/Tests/Editor/` (no asmdef needed for EditMode); in tests, build boards from readable strings (e.g. `"1,1,0,0|0,0,0,0|..."`) instead of `int[,]` literals — same readability, no compiler quirks.

## Unity/MCP gotchas (verified)
- `execute_code` compiles with CodeDom (C# 6) which **mangles multi-dimensional array literals** (it transposes `int[,] { { ... } }` initializers). In snippets, build arrays programmatically (cell by cell); never trust a snippet that passes `int[,]` literals.
- After creating scripts, wait for compilation + domain reload to finish before running `run_tests`: running too early fails initialization or returns stale results (the editor may still be running the previous assembly). If test results contradict the source on disk, force a clean recompile (refresh with compile request) and re-verify.
- If compiled behavior differs from the `.cs` on disk, inspect the compiled assembly before touching the logic: fixture literal data ends up in `<PrivateImplementationDetails>` static fields and member calls can be resolved via `Module.ResolveMethod`/`ResolveField` on the IL tokens.
