# TowerDefensive-FinalProyect

Unity 6 tower-defense game (3D, URP). No CI or README yet; Unity EditMode tests live under `Assets/_Custom/Tests/Editor/`.

## Stack (verified in ProjectSettings/Packages)
- Unity **6000.3.19f1**, URP **17.3.0** (Gamma color space), ProBuilder 6.1.2 (level geometry), Recorder 5.1.7
- **New Input System only** (`activeInputHandler: 1`): legacy `UnityEngine.Input` is disabled — use `UnityEngine.InputSystem` / PlayerInput components
- MCPForUnity (`com.coplaydev.unity-mcp`, git package) is installed: the unityMCP tools drive the editor, but only work while the Unity Editor is open with the bridge running
- No `.asmdef` files for our own scripts — default compilation (`Assembly-CSharp`). Exception: the vendored `Assets/_Custom/DamageNumbersPro/` asset package ships its own `DamageNumbersPro.asmdef`; the default assembly auto-references it, so `using DamageNumbersPro;` just works from any of our scripts.

## Layout
- All game content lives in `Assets/_Custom/` (`Scenes/`, `Scripts/`, `Prefabs/`, `Models/`, `Materials/`, `UI/`, `DamageNumbersPro/`); URP pipeline assets live in `Assets/URP/`. Keep new content inside `_Custom/`, never at Assets root.
- **Four scenes exist, only two are in Build Settings**: `Main Menu.unity` (scene 0, title screen, `MainMenuController`) and `0_Main.unity` (scene 1, the original gameplay level — Ground, Main Camera, Directional Light, Global Volume and the persistent `Board` object, named `Board 2048`, in Procedural mode). `LevelPrueba.unity` is a second, actively-developed level **not yet in Build Settings**: its `Tablero` drives `BoardManager` in **Anchored** mode over a teammate's hand-built map mesh (`Mapa`), its `Path` drives `PathBuilder` in **Manual** mode over a hand-placed waypoint chain the level's owner edits directly (see the PathBuilder gotcha below — don't touch `manualWaypoints` unless asked), plus the full HUD/economy/wave/bomb-powerup wiring. `UI_Sandbox.unity` is a bare scene with just a `UIDocument` for iterating on HUD views without loading gameplay. Add a scene to Build Settings only when explicitly asked.
- `Assets/_Custom/Scripts/` holds: board model/view (`BoardGrid`, `BoardManager`, `Tower`, `TowerVisual`), input (`InputController`), economy (`EconomyManager`), shop (`TowerShop`), combat (`TowerAttack`, `TowerProjectile`), the enemy road (`PathBuilder`), enemies (`EnemyHealth`, `EnemyFacing`, `EnemyHealthBar`, `EnemySpawner`), the player's lives (`PlayerBase`), the bomb-drag powerup (`BombDragAbility`, `ExplosionVisual`), castle feedback (`CastleDamageFeedback`, `CastleLowHealthFire`), the camera (`CameraEdgePan`) and `AudioManager` (volume singleton, `DontDestroyOnLoad`). `Scripts/Editor/` has the custom inspectors (`BoardManagerEditor`, `PathBuilderEditor`) plus the two generator tools (`EnemyPrefabBuilder`, `EnemyAnimatorBuilder`). `Assets/_Custom/Data/Towers/` holds the balance ScriptableObjects (`TowerLevel1..4.asset` + `TowerCatalog.asset`); `Assets/_Custom/Materials/` has `CellMaterial.mat` plus the hand-authored VFX materials `SmokePuff.mat`/`RedZoneIndicator.mat`/`ExplosionBlast.mat` (all `Sprites/Default` + the generated `Assets/_Custom/Textures/SoftCircle.png`, chosen after CFXR's Cartoon FX shaders rendered invisible in this project's URP setup — don't reintroduce CFXR); `Assets/_Custom/Models/Kenney Assets/Tower Defense/` holds the imported FBX tile/tower/detail models, `Assets/_Custom/Models/Enemies/` the skeleton models + animation rigs, `Assets/_Custom/Models/PowerUps/Bomb/` the bomb model/icon/prefab; `Assets/_Custom/Animations/` holds the generated `EnemyAnimator.controller`. `Assets/_Custom/Prefabs/` has `Towers/` (`Tower.prefab` + `tower1..6.prefab`), `Enemies/` (`Skeleton_*.prefab`, generated — see gotchas) and `VFX/` (Damage Numbers Pro popups: `DamageNumber.prefab` for combat damage, `GoldNumber.prefab` for currency earned, `BoomText.prefab` for the bomb explosion, plus `Projectile_Cannonball.prefab`). `Assets/_Custom/DamageNumbersPro/` is the vendored Damage Numbers Pro asset (fonts/materials/scripts) — don't edit it; its `Demo/` prefabs are useful only as a **read-only reference** for cloning a new popup style (see the DNP gotcha below). `Assets/_Custom/UI/Scripts/` (`GameHUDController`, `MainMenuController`) is the only place still using a `namespace` (`Custom.UI`) — pre-existing, kept as-is, see Code style. `Assets/_Custom/UI/Views/` and `Styles/` hold the UXML/USS for the HUD (`GameHUD.uxml`/`.uss`).

## Gotchas
- No CLI build/test/lint — verification happens in the Unity Editor: watch the Console for compile errors after script changes, then test in Play mode.
- `.meta` files are versioned (see .gitignore) and must never be deleted or recreated — they hold the GUIDs that scene/prefab references depend on. Create/move/rename assets only through the Unity editor (or MCP), never by hand. **Exception**: hand-authoring a whole new `.prefab`/`.mat` YAML file from scratch (not editing an existing one) is fine when mirroring a proven working asset field-for-field — that's how `GoldNumber.prefab`/`BoomText.prefab` were built from `DamageNumber.prefab`'s skeleton and DNP's own `Demo/` prefabs. Always compile-check (`refresh_unity` + `read_console`) right after.
- Script class name must match its file name; use URP-compatible shaders (e.g. `URP/Lit`), not Built-in RP shaders. For 2D/VFX overlays (particles, ground indicators, radial wipes) `Sprites/Default` is the proven cross-pipeline-safe choice in this project.
- Don't hand-edit scene/prefab `.unity`/`.prefab` YAML when an editor/MCP operation (or a C# script) can do the job.
- `BoardManager` uses `ExecuteAlways` and now supports two `mode`s. **Procedural** (`0_Main.unity`'s board): generates its own cubes, editable scene children live under `Board/Cells` and `Board/Towers`, size comes from `boardWidth`/`boardHeight` (rectangular now, not a fixed 4x4 — `BoardGrid` takes `Width`/`Height` separately; `Size` is kept only as a Width alias for old square-board callers). **Anchored** (`LevelPrueba.unity`'s `Tablero`): no cubes are generated — `anchoredCells` is an array of pre-placed Transforms (e.g. round bases from a teammate's map mesh) and `BuildAnchorGrid()` groups them by local X/Z (0.5 tolerance) to derive width/height and each cell's world position automatically; array order doesn't matter. Use the custom Inspector (or `SetEditorLevel`/`RebuildBoardView`) to change levels and rebuild the view; do not recreate `Cells`/`Towers` children manually, and in Anchored mode never generate cubes over the hand-placed markers.
- **Towers lock during a wave**: `BoardManager.Move()` returns immediately (no-op, not even buffered) whenever `spawner.IsRunning` is true, so 2048-style reordering only works between waves. Keep that check first in `Move()` if you touch it.
- Enemy/combat layer (merged from teammates, kept where they wrote it): `Assets/JeanAssets/Scripts/` has `Path` (waypoint list + gizmo), `TestEnemyMovement` (walks the waypoints, `ApplySlow` for the drone EMP) and `Tower/TowerTargetDetector` (OverlapSphere on the **Enemy** layer, picks the closest, aims the tower). `Assets/JeanAssets/Scripts/Drone/` has the drone's own ability set (`BombAbility`, `EMPAbility`, `RepairAbility`, `RepulsionAbility`, switched by `DroneAbilityController` with its own independent cooldown/charge system) plus `DroneController`/`DroneDeployment`/`DroneFlightArea` — `DroneAbilityController` is **not** connected to the HUD's ability slots or its cooldown system, it's the drone's own separate input-driven loop (`Assets/JeanAssets/Prefabs/DroneSystem.prefab`). `Assets/Enemies/RutaEnemigo.cs` is an older NavMesh experiment — **not used**, the fixed path is waypoint-based. Only add to those files, never rewrite them; the additions so far are `Path.SetWaypoints`, `TestEnemyMovement.SetPath`/`Finished`, `TowerTargetDetector.CurrentTarget`/`SetDetectionRange`/`SetEnemyLayer`, and on `BombAbility`: `explosionDamage`, `ExplodeAt(position)` (explosion at a known point, skipping `DropBomb`'s downward raycast — used by `BombDragAbility`), `explosionVisualMaterial`/`explosionVisualDuration` (spawns `ExplosionVisual` sized to `explosionRadius`) and `boomTextPrefab`/`boomTextHeightOffset` (spawns the "Boom" DNP popup) — all fired from the shared `DetectEnemies()` so both `DropBomb()` and `ExplodeAt()` get identical feedback.
- `PathBuilder` (`ExecuteAlways`, child of the board) has two `mode`s. **Procedural** generates the enemy road: a squared **C** around the board — `BuildPathPoints()` is pure math (16 tiles for a 4x4 board, ring at `boardCells*tileSize/2 + tileSize/2`), then it creates `Tiles/` (mesh normalized to `tileSize`, top face at `surfaceY`, BoxCollider on the **Floor** layer for the drone bomb) and `Waypoints/`, and feeds them to `Path`. Tile rotation is a guess from the walking direction plus a per-type yaw offset in the Inspector — the waypoints (i.e. the movement) never depend on that guess. **Manual** (`LevelPrueba.unity`'s `Path`) generates nothing: `manualWaypoints` is an ordered Transform array (first = spawn, last = castle front) that `LinkManualWaypoints()` feeds straight to `Path`, meant for a road already traced by hand over a teammate's mesh/map. **When a level's `PathBuilder` is in Manual mode and its owner is actively trimming `manualWaypoints` by hand, don't touch that array or regenerate the path — ask before changing waypoint count or order**, even if the count looks inconsistent with a stated target; it may be mid-edit.
- Enemy assets are **generated, never hand-made**: the menu `Tower Defense > Crear prefabs de enemigos` (`EnemyPrefabBuilder`) turns every loose model in `Models/Enemies/` (skipping `Rig_*` and the `Props & weapons/` subfolder) into a prefab in `Prefabs/Enemies/` with the Enemy layer, a CapsuleCollider measured from the real bounds, `TestEnemyMovement` + `EnemyFacing` + `EnemyHealth` and the Animator, then wires the scene's `EnemySpawner` and the `PathBuilder` waypoint height. Re-run it after adding a model instead of editing prefabs by hand. `Assets/Enemies/` (Johan's old NavMesh test) contains **no** enemy assets — don't look for them there.
- `EnemyAnimatorBuilder` builds `Animations/EnemyAnimator.controller` from the clips inside `Rig_Medium_MovementBasic` (`Walking_A/B/C`, `Running_A/B`) and `Rig_Medium_General` (`Death_A/B`, `Hit_A/B`, `Idle_A/B`, `Spawn_Ground`...): two states, `Walk` (default, and the tool forces `loopTime` on that clip via `ModelImporter`) and `Death`, reached from Any State by the **`Die`** trigger — the same string as `EnemyHealth.dieTrigger`. The Animator lives on the model child (that's where the bones are) with `applyRootMotion = false`, because the movement belongs to `TestEnemyMovement`. Before touching clips, `EnsureController()` calls `ShareAvatarAcrossRigs()`: the `Rig_*` FBX files carry no mesh, so Unity can't build a humanoid avatar for them on its own (they import with `avatarSetup: NoAvatar`) — the tool points every `Rig_*` at `Skeleton_Warrior`'s avatar (`ModelImporter.avatarSetup = CopyFromOther` + `sourceAvatar`) and reimports, skipping any rig already pointed there by hand. If a new `Rig_*` is added, re-running the menu wires it automatically. Both current rigs are confirmed pointed at `Skeleton_Warrior` (`avatarSetup: CopyFromOther`) as of this writing — if that ever reads back as `NoAvatar`, the menu was run while the editor script assembly was still mid-recompile; just re-run it after compilation finishes.
- `EnemyHealth.Die()` pays the reward (`EconomyManager.AddCurrency`, optionally spawning `goldPopupPrefab` at the death position — see the Damage Numbers Pro gotcha), fires `Died` (so `EnemySpawner` can decrement its alive count — see below), **disables the movement and every collider** (so towers stop shooting a corpse), fires the death animation and destroys the object after `deathDelay`. Keep that order if you touch it. `Setup(health, money, economy, goldPopupPrefab = null)` — the last argument is optional so old 3-arg call sites (tests, `TowerAttackTests`) keep compiling.
- `EnemySpawner` prepares each enemy it creates (`SetPath`, `EnemyHealth.Setup(..., goldPopupPrefab)`, destroy on `Finished`), so the enemy prefabs need no scene references. It self-wires in `EnsureReferences()`: `pathBuilder`/`economy` are found via `FindFirstObjectByType` if left empty, `playerBase` resolves through `PlayerBase.Instance` (see below — don't have it do its own `FindFirstObjectByType` for `PlayerBase`). `enemyPrefabs` is an array; each spawn picks one at random (`PickEnemyPrefab`), so a wave is never visually uniform. **A wave only counts as finished when every enemy that spawned is dead or has reached the end** — `AliveCount` tracks enemies still alive, incremented on spawn and decremented by `HandleEnemyDied` (subscribed to `EnemyHealth.Died`) and `HandleEnemyFinished`; `WaveFinished` fires only once spawning is done **and** `AliveCount <= 0`, not just when the last enemy has left the spawner. `EnemyReachedEnd` fires whenever an enemy reaches the castle (used by `CastleDamageFeedback`), separate from `PlayerBase.LivesChanged` so castle-hit feedback doesn't assume "losing lives" always means this.
- `PlayerBase.Instance` is the single point of access for the player's lives: everything that needs `PlayerBase` (`EnemySpawner`, `GameHUDController`, `CastleLowHealthFire`) should read `PlayerBase.Instance` instead of doing its own `FindFirstObjectByType<PlayerBase>()` — if every script searches independently, `Awake`/`Start` ordering can make one create its own instance before another finds it, desyncing the HUD from the real lives. `Instance` lazily finds (or, only in Play Mode, creates) the single shared object. Defeat (the `Defeated` event, shown as the HUD's defeat screen) fires **only** from `PlayerBase.TakeDamage` reaching 0 lives — there is no debug key for it (a `D` debug key existed early on but conflicted with `InputController`'s WASD tower movement and was removed).
- Wave difficulty scales per wave (2026-08-20). `EnemySpawner` has an "Aumento por oleada" block (`healthGrowthPerWave`, `speedGrowthPerWave`, `shooterDamageGrowthPerWave`, `shooterChanceGrowthPerWave`, `enemiesGrowthPerWave`) and the spawner reads **`Get*ForWave(waveNumber)`** rather than the raw fields when building an enemy. Growth is **linear, not compounding** (`base * (1 + growth * (wave - 1))`) so wave 5 at 0.5 is +200%, not +406% — deliberate, so the numbers stay predictable and don't explode in late waves; `enemiesGrowthPerWave` is a flat `+N` integer instead of a percentage for the same reason. `GetEnemiesForWave` returns 0 when `enemiesPerWave` is 0, preserving the "endless wave" meaning instead of scaling it into a finite one. All values are computed **per spawn, not frozen at `StartWave`**, so editing a number mid-wave in the debug window affects the next enemy that comes out. Covered by `EnemyWaveScalingTests`.
- **Level2 and Level3 were built out into playable levels** (2026-08-20). Both were pure decorative geometry before (no `BoardManager`, spawner, path, HUD or `InputController` at all). The managers were brought over by **additively loading `LevelPrueba` and instantiating its `Managers` / `UI` / `AbilityGround` roots into the target scene**, then closing it — that's the fastest way to get an identical, fully-wired HUD (UIDocument + PanelSettings + every AudioClip + cooldown configs) instead of rebuilding it field by field. After copying, the scene-specific references still have to be re-pointed by hand (`TowerShop.board/economy/inputController/spawner`, `BoardManager.inputController/spawner`, `EnemySpawner.castleTransform`); most of the rest self-resolves through the `FindFirstObjectByType` fallbacks these components already have. Enemy routes are `PathMode.Manual` `PathBuilder`s built from the map's own road tiles — **waypoints only need to sit at turns**, not on every tile, and the walking height is **y = 1.21** (the road tiles' top surface is 0.61 and enemies ride 0.60 above it; the same tile assets are used in every level, so this number holds). Both scenes' cameras were repointed from a side-on "showcase" angle to `rot (54,0,0)` matching `LevelPrueba`, with `CameraEdgePan` limits framing the playable band from the spawns up to the castle. Level2 has 3 entrances feeding one central board; Level3 has 6 entrances, all routed so every one passes either the central board (road x=0) or the left board (road x=-12) — a route that reaches the castle without passing a board can't be defended at all, so check that when adding entrances.
- **Enemy types per wave + Johan's flying skeleton, and the boss moved to the end of its wave** (2026-08-25): `EnemyTypeEntry[] EnemySpawner.enemyTypes` (label, prefab, weight, minWave, maxWave — maxWave 0 = no upper limit) lets each enemy prefab have its own wave window, weighted-random among whatever's active for the current wave (`PickEnemyPrefab(waveNumber)` → `PickFromEnemyTypes` → falls back to the old flat `enemyPrefabs` list, unweighted, any wave, if `enemyTypes` is empty or nothing in it is active yet for that wave — so old scenes/tests that never touch `enemyTypes` are unaffected). Editable from Game Debug's new "Tipos de enemigo" section, and the "Ver como quedan las proximas oleadas" table grew a "Tipos / Jefe" column (`EnemySpawner.DescribeActiveEnemyTypes`) so you can see at a glance which types are live on which wave and whether the boss lands there. **Johan's "esqueleto volador" (`Assets/_Custom/Prefabs/Enemies/Lght Flying Skeleton.prefab`, from his `EnemiesIAJohan` branch, commit `enemigo volador ligero` — cherry-picked in since that branch was never fully merged) is wired into all three levels' `enemyTypes` starting wave 4**, alongside the four regular skeletons (unrestricted, same as before). It's a composite prefab: the root carries all the usual logic components (`TestEnemyMovement`/`EnemyHealth`/etc.), and a child `Skeleton_Minion (3)` rides inside a barrel-with-propeller visual with its own copy of those same components **disabled** — don't re-enable them, the root is the one actually driving it. The propeller spin is `RotarHelice.cs` (`Assets/Enemies/RotarHelice.cs` — renamed from `RutaEnemigo.cs` in the same cherry-picked commit), a two-field rotate-on-Update script, already wired in the prefab. — Separately, `bossWave` (now defaults to 10, all three scenes updated to match) no longer spawns the boss at `StartWave()`; it spawns from `Update()` the first time `doneSpawning` goes true for that wave (i.e., once every normal enemy of that wave — scaled count included — has been sent out), guarded by a `_bossSpawnedThisWave` one-shot flag (without it `SpawnBossIfDue` would fire every single frame once spawning is done, since that condition stays true for the rest of the wave). Spawning the boss inside that same `doneSpawning` block, before the `_aliveCount <= 0` check, is what keeps the wave from closing in the same frame it should still be blocked by the boss. This is untestable in EditMode (`Update()` no-ops when `!Application.isPlaying`), so the automatic timing was verified live in Play Mode instead; `EnemyTypesAndBossTimingTests` only covers the parts that don't need a frame tick (weighted type selection, and that `StartWave()` alone no longer creates a `BossEnemy`). Gotcha hit while writing those tests: `CreateEnemy()` instantiates enemies/bosses as scene-root objects, not parented under the spawner, so a naive `[TearDown] { Destroy(_root); }` leaks them across tests — a leftover boss from one test gets picked up by another test's `FindFirstObjectByType<BossEnemy>()`. Fixed by also destroying every `EnemyHealth` found in the scene on teardown (the one component `CreateEnemy` always adds, even to a bare test placeholder).
- **Boss (golem)** (2026-08-20): `EnemySpawner.bossWave` picks the wave it appears on (0 = never), with `bossPrefab`/`bossHealth`/`bossSpeed`/`bossReward`/`bossSourceIndex` beside it, all editable from Game Debug's "Jefe" section (which also has a "Sacar el jefe ahora" button). One boss spawns at `StartWave` on that wave, *in addition to* the normal enemies. The whole point is `BossEnemy`: when it reaches the end of the path, `EnemySpawner.HandleEnemyFinished` **does not destroy it and does not decrement `_aliveCount`** — instead it calls `StartAttackingCastle`, which disables `TestEnemyMovement` and starts hitting `PlayerBase` for `damagePerHit` (2) every `secondsBetweenHits` (5). Because it still counts as alive, the "wave ends when nobody is alive" rule means **the wave cannot finish until the boss is killed** — that's the mechanism that forces you to defeat it, not a separate check. The prefab is `Assets/_Custom/Prefabs/Enemies/Boss_Golem.prefab`, built to the same shape as the skeletons (logic on the root, model + `Animator` on a `Visual` child) from the Humanoid Giant asset, driven by `Assets/_Custom/Animations/GolemAnimator.controller` (Walking default / `Attack` trigger / `Die` trigger — the same `Die` trigger name `EnemyHealth.dieTrigger` already uses). The FBX's Walking clip ships with `loopTime` off; it's switched on via `ModelImporter.clipAnimations`, otherwise the golem walks once and freezes.
- **Spawn arrows** (2026-08-20): `SpawnArrowIndicator` floats a red arrow over every entrance so you can see where enemies will come from, and hides them permanently on the **first** `WaveStarted` (they're a one-time presentation aid, not a persistent HUD element; it also skips building them at all if `WaveNumber > 0`, e.g. a mid-game reload). The arrows are a small procedural mesh lying flat in XZ and rotated toward the *next* waypoint, so they read as a direction from the top-down camera.
- **Multiple enemy entrances** (2026-08-20): `EnemySpawner.spawnSources` is an array of `SpawnSource` (own `pathBuilder`, `startWaypointIndex`, `enemiesPerWave`, `spawnInterval`, `startDelay`, plus `healthMultiplier`/`speedMultiplier` that scale on top of whatever the wave already computed). **Empty array = the original single-entrance behavior**, so existing levels are untouched; with sources present, `enemiesPerWave`/`spawnInterval` on the spawner become the fallback that any source leaves at 0 inherits. Each source keeps its own timer/count (`_sourceTimers`/`_sourceSpawned`, rebuilt per wave) and the wave only ends when **every** source finished *and* `AliveCount <= 0` — a source with `enemiesPerWave` 0 is endless and keeps the wave open forever. `SpawnEnemy()` and `SpawnFromSource()` both funnel into `SpawnEnemyInternal(path, waypointIndex, healthMul, speedMul)`.
- **Defeating the boss now actually wins the level** (2026-08-25). `EnemySpawner.WaveFinished` already fired correctly after the boss wave (the boss counts as alive, so the wave can't close until it's dead — see the boss-timing entry below), but nothing was listening for "was that the boss wave" — `GameHUDController.OnWaveFinished` just reset the wave button every time, win or not. Fixed by checking `IsBossWaveJustCleared()` (`spawner.WaveNumber == spawner.bossWave`, with `bossPrefab`/`bossWave` both set — a level with no boss configured never wins on its own, unchanged from before) and calling the already-existing `ShowVictoryScreen(isFinalLevel)`, with `isFinalLevel` from `gameFlow.GetLevelNumber(...) >= gameFlow.LevelCount`. Verified live on both branches: LevelPrueba (level 1 of 3) shows "¡VICTORIA!" with Menú Principal/Siguiente Nivel and correctly resolves the next scene as Level2; Level3 (the last one) shows "¡FELICITACIONES!" (`_gameCompleteOverlay`, not `_victoryOverlay`) with Menú Principal/Ver Créditos. **Gotcha worth flagging for whoever else drives this via `unity command eval`:** `capture_game_view` defaults to `source=camera`, which renders the 3D scene only and **completely misses UI Toolkit Screen Space Overlay** — the HUD, victory screen, all of it. Pass `--source screen` (Play Mode only) to actually see the UI in the screenshot; the default silently produces a normal-looking gameplay screenshot with no indication the overlay was missed. Also: `victory.style.display.value` reads as a **misleading `Flex`** even when the element was never touched (untouched `StyleEnum<DisplayStyle>` defaults to enum value 0, which happens to be `Flex`) — check `.style.display.keyword` (`Null` = never set, `Undefined` = explicitly assigned) or just use `.resolvedStyle.display`, which reflects what's actually rendered.
- **Ballista aiming + global economy** (2026-08-25). Two real bugs behind "las ballestas no atinan y no hacen daño". (1) `CrossbowRainAttack.GetPredictedPosition` used `movement.transform.forward` **as if it were velocity** — it's a unit vector, so the lead was a flat 0.2 units no matter how fast the enemy moved — and led by a fixed `predictionTime` instead of the arrow's actual travel time. With `ArrowData.speed = 5` and a target 8 units out, real flight is ~1.6s and the needed lead ~3.6 units, so arrows landed ~3.4 units behind (an enemy is ~1 unit wide). Fixed to `forward * CurrentSpeed * (distance / arrowSpeed + predictionTime)`, which needed a new `TestEnemyMovement.CurrentSpeed` getter (`movementSpeed` was private, so callers could only get direction); `maxPredictionDistance` raised 1.5→8 because the old cap was *smaller than the correct lead* and would have clipped the fix. Note the damage itself never actually missed — `CrossbowProjectile.HitTarget` applies damage to the stored target regardless of where the arrow lands — so this was a visual miss that only cost real damage when the target died mid-flight. (2) The `Normal` arrow did **1 damage**: 9 arrows per ~9s cycle = 1 DPS for 100 gold, against 5 DPS from a 50-gold tower. Now Normal 8 / Ice 7 / Poison 10 / Fire 13, all speed 5→14, and `attackCooldown` 8→5 (in 8s an enemy at speed 2 covers 16 units and crosses the whole 10-unit search radius, so the ballista fired once per group and sat mute). Measured after: a well-placed ballista clears wave 1 (6/6, no lives lost) and falls off by wave 6 (0 kills vs 35 HP enemies) unless you buy a better arrow — Fire gets 3 kills there. That falloff is deliberate: no single 100-gold purchase should carry the run. **Watch out when testing ballistas: the six `CrossbowSlot` positions are not equivalent.** Sampling path points against each slot's 10-unit radius, `CrossbowSlot (2)` has 108 path points in range but the bare `CrossbowSlot` has only **3** (nearest road 9.9 units away, right at the edge) — it is effectively a dead slot. `FindObjectsByType` order varies per play session, so `slots[0].Unlock()` picks a different slot each run; several confusing "the ballista kills nothing" measurements were just that dead slot. Pick slots by name, not index. — Separately, **gold is now global** in `Assets/_Custom/Data/GameEconomyConfig.asset` (a ScriptableObject like `GameFlowConfig`), read by `EconomyManager`/`TowerShop`/`EnemySpawner`/`GameHUDController`, each falling back to its own serialized value when the config is unassigned. Before this the numbers lived in four separate per-scene components and had already drifted (LevelPrueba/Level2 started at 150 gold, Level3 at 200 — not a design decision, just separate edits). Values: start 200, tower 50, enemy reward 10, wave bonus 50, ballista 100, arrow unlock 150→120, arrow switch 50→25 (switching between *already-owned* arrows is a per-wave tactical call; at the price of a whole tower nobody used it). Fixing this surfaced a latent bug in `TowerShop`: `TowerCost` (shown in the UI) and `TrySpend(towerCost)` (actually charged) read different fields, so a config-driven price would have displayed one number and charged another. `EconomyManagerTests`/`TowerShopTests` asserted the literal 150 default and now pin their own balance via `SetMoney`, so tuning gold no longer breaks unit tests.
- **Level3 wave balance** (2026-08-25): fixed a real bug and a real design gap while balancing the 6-entrance level. Bug: `SpawnSource.enemiesPerWave > 0` (which Level2 and Level3 both use, one nonzero value per entrance) bypassed `GetEnemiesForWave`'s growth entirely — the count stayed flat forever, no matter the wave. Added `SpawnSource.enemiesGrowthPerWave` (mirrors the general field) and `GetEnemiesForSource` now applies the same linear formula per-source when `enemiesPerWave > 0`; a source left at 0 is unaffected (still just inherits the general curve). Level2's sources still have `enemiesGrowthPerWave = 0` (flat forever) — not touched, since only Level3 was in scope, but the same fix applies if it's ever asked for. Design gap, found only by actually playing it rather than reasoning about the numbers: **the two boards each have exactly one "golden" corner cell that sees all 6 entrances at once** (the corner nearest where the paths converge), a handful of cells that see 4 of 6, and several dead cells that see nothing — verified by sampling points along every path and measuring distance to every anchored cell. A scripted test that bought towers via `PlaceTowerRandom` and never repositioned them lost 11 of 20 lives and a tower in wave 1 alone; the same starting resources, after sliding each board toward its golden corner with `board.Move(...)` (Left reaches Tablero's corner at local x=0, Right reaches Tablero2's at local x=2), lost only 2. Sliding two towers onto the same cell **merges them into a higher tower level** (confirmed live: two level-1s became one level-2, `Grid.GetLevel` went from 1 to 2) — this is the real, if non-obvious, upgrade path for towers, since `TowerShop`/`PlaceTowerRandom` only ever place level 1 directly. Net changes: `startingMoney` 150→200 (4 starting towers instead of 3, needed against 6 simultaneous entrances), and every `SpawnSource`'s `enemiesPerWave`/`enemiesGrowthPerWave`/`spawnInterval` retuned so the three route "families" scale differently — **Abajo** (borderline ~4.7-5.0 units from both boards, meaning it's also barely inside *tower* range, not just outside shooter range as the distance alone suggests — only 4/12 cells per board ever reach it) grows slowest (0.18); **Lejos** (longest paths, but the ones with the *best* cell coverage — up to 8/12) grows fastest (0.45); **Medio** (shortest paths, least reaction time) stays lowest always (0.12). Growth rates were deliberately staggered so the four non-Medio sources don't all cross an integer threshold on the same wave (that was causing a jarring +4 spike at wave 3 in an earlier pass). Covered by `SpawnSourceGrowthTests`.
- In **Anchored** mode `BuildAnchorGrid` assigns columns/rows from each anchor's **world** X/Z, not its local position (it still *stores* the local position, which is what `AnchorLocalPosition` needs to place towers). This matters because the player presses "right" thinking in screen space and the camera is world-aligned: `Level2`/`Level3` have their `Tablero` rotated 90° on Y, so grouping by local axes made the grid's X run along world Z and "right" visibly moved towers *down*. `LevelPrueba`'s board is unrotated, which is why the bug stayed hidden until other levels existed. Covered by `BoardAnchoredOrientationTests` (which builds rotated boards on purpose).
- **Two independent boards in one level** (2026-08-20, set up in `Level3`): `BoardManager.acceptsInput` gates `HandleMoveRequested`, and `BoardSelector` (one per scene) flips it so only the chosen board answers the keys — without it both boards move on the same keypress, since each `BoardManager` subscribes to the same `InputController.MoveRequested`. Cycling is `Tab` (`InputController.NextBoardRequested`). The selected board is marked with a translucent plate (`BoardSelector`, material `Assets/_Custom/Materials/BoardHighlight.mat`, `Sprites/Default`) positioned **below** the cells (`highlightHeight` is negative on purpose) — it deliberately does **not** tint the cells, because `BoardLockFeedback` already writes `_BaseColor` on them for the wave-lock warning and the two would fight over the same property. `Level3`'s `Tablero`/`Tablero2` were pre-existing decorative meshes; they now carry real `BoardManager`s in **Anchored** mode using their 12 `tower-round-base` children as cells (4x3 each) — note `boardWidth`/`boardHeight` only get recomputed by `BuildAnchorGrid` on a rebuild, so after assigning `anchoredCells` from code you must call `RebuildBoardView()` or the serialized size stays stale.
- `EnemySpawner.spawnWaypointIndex` picks which `Path` waypoint enemies come out of (0 = the normal start), for testing the end of the route without walking the whole thing. It requires `TestEnemyMovement.SetStartWaypoint(index)` — without it the enemy spawns at the right place but its `currentWaypoint` stays 0, so it walks *backwards* to the start of the path.
- **Play-Mode tuning survives exiting Play Mode** (2026-08-20) via `SpawnerTuningStore` (`Scripts/Editor/`): press "Guardar estos valores al salir de Play Mode" in the debug window, and an `[InitializeOnLoad]` hook on `playModeStateChanged` copies them back onto the scene's `EnemySpawner` when Edit Mode returns (then you still need Ctrl+S). Two deliberate constraints: it stores **only primitives, never `UnityEngine.Object` references** (a prefab/manager reference captured in Play Mode would come back as a dangling instance ID), and it records the scene path and refuses to apply if a different scene is open when you exit. State lives in `EditorPrefs`, not a static field, because exiting Play Mode triggers a domain reload that would wipe statics.
- `CameraEdgePan` (on `Main Camera`) pans the view when the pointer reaches a screen edge, clamped to a per-level XZ rectangle (`limitMin`/`limitMax`) so the level can't be lost off-screen. **The limits are per-scene**: every playable scene needs its own (both `LevelPrueba` and `1_Tutorial` have them) — configure from Tower Defense > Game Debug ("Camara" section), which draws the rectangle in the scene view with draggable handles and has an "Ajustar al camino" button that fits the limits to the `Path` waypoints. Three things that are deliberate and easy to get wrong if rewritten: (1) it moves along `transform.forward` **flattened onto the XZ plane** — the camera is tilted ~54° down, so using its raw forward would fly it into the ground instead of panning; (2) it uses `Time.unscaledDeltaTime`, because at x2/x3 game speed a scaled `deltaTime` would make the camera race; (3) it skips panning entirely when `Time.timeScale == 0`, which is the shared signal for "a modal is open" (pause/victory/defeat all freeze that way) without having to couple the camera to the HUD. It also ignores the pointer when it's outside the window bounds — in WebGL the last position stays frozen at an edge, which would otherwise pan forever. Limits constrain the **camera position**, but "Ajustar al camino" compensates for the camera→focus offset so the numbers frame the path, not the camera; a margin of 0 means the focus can reach exactly the path's bounding box (raising it starts letting empty void into frame).
- Castle feedback, both listening to events instead of polling: `CastleDamageFeedback` flashes red + scale-punches the castle's renderers (MaterialPropertyBlock, same technique as `TowerVisual`'s pulse) on `EnemySpawner.EnemyReachedEnd`. `CastleLowHealthFire` (renamed 2026-08-19 from `CastleLowHealthSmoke`, same script GUID via `AssetDatabase.MoveAsset` so scene references survived — see gotchas below) instantiates a real VFX prefab (`firePrefab`, e.g. `Assets/_Custom/Casual RPG VFX/Prefabs/Fire/Fire_medium.prefab`) once, inactive, as a child, and toggles it via `SetActive` + `ParticleSystem.Play()`/`Stop(true, StopEmittingAndClear)` whenever `PlayerBase.LivesChanged` crosses **half of `PlayerBase.maxLives`** (computed live, not a fixed threshold field), while lives are still above 0. Both `LevelPrueba` and `1_Tutorial` have their own `Castillo` with this component — a scene-level rename like this leaves old serialized fields (`smokeMaterial`, `smokeOffset`, etc.) as harmless orphaned YAML and a stale `m_EditorClassIdentifier` string (cosmetic only, Unity resolves the component by the `m_Script` GUID) but does **not** carry `firePrefab` over — check every scene with the old component for a null `firePrefab` after a rename like this, not just the one you were testing in.
- Wave flow: `spawnOnStart` is **false** — the wave starts from the HUD's *EMPEZAR OLEADA* button. `StartWave()`/`StopWave()` fire `WaveStarted`/`WaveFinished` events and `WaveNumber`/`IsRunning` are public; the HUD (`GameHUDController`, UI Toolkit, object "UI") subscribes to them to hide/show the button, show *OLEADA N*, reset any `PerWave`-limited ability use count (see below), and to `EconomyManager.MoneyChanged` for the coin counter. The button is the only way to start a wave (there's no auto-start); a wave only ends per the "all enemies dead or escaped" rule above, then the button comes back.
- The bomb powerup (ability slot 1 in the HUD) is a drag-and-drop, not a click: `BombDragAbility` (on a `Managers` object) holds a floating preview of `bombPrefab` under the pointer plus a blinking ground indicator (`indicatorMaterial`, plane-raycast against `groundHeight`), driven by `GameHUDController.OnAbility1PointerDown`/`PointerUp` (registered `TrickleDown` — the `Button`'s own `Clickable` consumes bubble-phase `PointerDown` first, so a bubble-phase handler would never see it) and polled each `Update()` via `Pointer.current` while dragging. `EndDrag()` instantiates the prefab and runs `FallAndExplode` (a smooth `AnimationCurve`-eased drop, not instant), which on landing gets-or-adds a `BombAbility` and calls `ExplodeAt(groundPosition)` — reusing Jean's drone bomb system end to end (radius, damage, visual, "Boom" text all identical for both bomb sources).
- Ability cooldown + usage limits live entirely in `GameHUDController`: each of the 4 slots has its own `PowerUpCooldownConfig` (`ability1Cooldown`..`ability4Cooldown`, public fields — edit cooldown seconds, `usageLimitMode` `Unlimited`/`PerMatch`/`PerWave`, `maxUses` per slot straight in the Inspector, no code changes needed to reconfigure a slot or swap which powerup uses it) plus a private `AbilitySlot` runtime wrapper built once in `OnEnable`. `CanUseAbility` gates (read-only), `ConsumeAbility` starts the cooldown and decrements uses; ability 1 gates on `PointerDown` and only consumes on a successful drop (`EndDrag()` returning non-null — a drag released off-board doesn't cost a use), abilities 2-4 gate+consume atomically on click once unlocked. `PerWave` uses reset in `OnWaveStarted`. The radial "clock" cooldown overlay is drawn with UI Toolkit's `generateVisualContent` + `Painter2D.Arc` on a `CooldownOverlay` child VisualElement per slot (a dark pie wedge from 12 o'clock, sweeping clockwise, shrinking as the cooldown recharges; stays fully covered if `usageLimitMode` uses are exhausted) — this is the only place in the project using `Painter2D`.
- SFX (2026-08-20, `Assets/SFX/`): no central sound registry — every script that plays a sound owns its own `AudioClip` field (`hoverSound`/`clickSound` on `GameHUDController` was the original pattern; combat/ability scripts now follow it too), assigned per-scene/per-prefab in the Inspector. One-shots go through `AudioManager.Instance.PlaySFX(clip, randomizePitch)`, which wraps a single shared `AudioSource.PlayOneShot` — fine for one-off hits but **can't loop or be positional**, so anything that needs to (enemy footsteps on `TestEnemyMovement`, the castle's fire crackle on `CastleLowHealthFire`) creates its **own** `AudioSource` (`loop = true`, `spatialBlend = 1`) instead, started/stopped alongside whatever already gates that effect (`OnEnable`/`OnDisable` for footsteps — piggybacking on `TestEnemyMovement` already being disabled on death/arrival — and the fire's own `SetActive` toggle). `TowerAttack` isn't baked into the tower prefabs (see `BoardManager.ApplyTowerAttack` below), so its `shootSound`/`impactSound` live on `BoardManager` (`towerShootSound`/`towerImpactSound`) and get copied on exactly like `projectilePrefab`/`damagePopup` already were. **`AudioManager` only exists in `Main Menu.unity`/`UI_Sandbox.unity`** (it's a `DontDestroyOnLoad` singleton created there) — jumping straight into `LevelPrueba`/`1_Tutorial` via a Play-Mode-start-scene override leaves `AudioManager.Instance` null and every sound in the game silently no-ops; for MCP testing, spawn a throwaway `GameObject` with `AddComponent<AudioManager>()` first. Also, unlike the `DamageNumbersPro` popups (which read `unscaledTime`), **`AudioSource` playback ignores `Time.timeScale` entirely** — the "slow timeScale way down to get a wide window to screenshot a fast effect" trick from the popup/VFX gotchas below does nothing for verifying a sound fired; instead call the effect's synchronous entry point directly (e.g. `BombAbility.ExplodeAt(pos)` instead of dragging the bomb through its `AnimationCurve` fall) and check `AudioSource.isPlaying` on the same call.
- Damage Numbers Pro (`Assets/_Custom/DamageNumbersPro/`, vendored) drives every floating combat/reward text via `Prefabs/VFX/*.prefab`, each a `DamageNumberMesh` (`DamageNumber` abstract base) root with `MeshA`/`MeshB`/`TMP` children — **found by name** (`transform.Find`), not by hierarchy order, so child order in a hand-authored prefab doesn't matter. `.Spawn(position, ...)` instantiates and returns the live instance; `Start()`/pooling/fade only run on the **next frame**, so a script that spawns-and-immediately-inspects in the same call will see an empty `activeInstances` — wait a frame (or grab the returned instance directly and set fields on it, which is safe pre-`Start()`) before asserting on it. To make a new popup style: find the matching preset under `DamageNumbersPro/Demo/Prefabs/3D/*.prefab` (2D/UI variants also exist), copy its `DamageNumberMesh` field values and its font/material `guid`+`fileID` pair (the DNP style `.asset`s under `DamageNumbersPro/Materials/*/` are self-contained TMP Font Assets — one guid serves both `m_fontAsset` and `m_sharedMaterial`, at different `fileID`s) onto a hand-authored prefab cloned from `DamageNumber.prefab`'s skeleton (that's how `GoldNumber.prefab`/`BoomText.prefab` were built). `EnemyHealth`/`EnemySpawner` wire `goldPopupPrefab`; `BombAbility` wires `boomTextPrefab`.
- Towers get their `TowerAttack` from `BoardManager`, not from the prefab: the **Combate** header (`towersAttack` toggle + `towerCatalog`) drives `BoardManager.ApplyTowerAttack`, which adds `TowerAttack` (bringing `TowerTargetDetector` with it) to every tower on create/refresh and hands it the catalog. Turning `towersAttack` off leaves towers purely decorative — no component added. `TowerAttack` itself reads damage/range/attackRate from `TowerCatalog` by `Tower.Level` (this is what finally wires the ScriptableObjects in `Data/Towers/`), pushes the range and the Enemy layer into `TowerTargetDetector`, and calls `EnemyHealth.TakeDamage`. Merging towers therefore upgrades their firepower for free. `IsInRange`/`Shoot`/`RefreshStats` are public specifically so `TowerAttackTests` can drive real `Physics.OverlapSphere` detection without waiting on `Update`.
- Visible combat: `BoardManager`'s **Combate** header also carries `projectilePrefab` and `damagePopup`, pushed to every `TowerAttack` on refresh. When `projectilePrefab` is set, `TowerAttack.Shoot` spawns a `TowerProjectile` (homing, `Projectile_Cannonball.prefab` with the cannonball FBX child) that deals the damage on arrival; otherwise the old instant-damage path runs. On hit the projectile spawns the Damage Numbers Pro popup (`Prefabs/VFX/DamageNumber.prefab`) at the impact point. `TowerProjectile.MoveStep` is public for EditMode tests (watch: a destroyed Unity object compares `== null` but fails `Assert.IsNull` — use `Assert.IsTrue(x == null)`).
- Enemy health bars: `EnemyHealth.Awake` adds an `EnemyHealthBar` when `showHealthBar` (default true) — the bar is a billboard (two unlit quads: Background + Fill) under a `HealthBar` child that rotates toward the camera without rotating the enemy root. Fill width/color follow `CurrentHealth/maxHealth`; the bar hides when the enemy dies. Its local position is the public `Vector3 barOffset` (default `(0, 1.5, 0)`) — edit X/Y/Z directly in the Inspector; there is no auto-computation from the collider anymore.
- Buy tower flow is `InputController.BuyRequested` (key **B**, temporary until UI) → `TowerShop.TryBuyTower()` → `EconomyManager.TrySpend()` → `BoardManager.PlaceTowerRandom(1)`. Buying is blocked (no money spent) when the board has no free cells.
- `BoardGrid.Move()` returns a `MoveResult` with `TowerMoveEvent`/`TowerMergeEvent` lists (deterministic, used to animate). In Play Mode `BoardManager` animates slides and merge pulses via coroutines (no external tweening); **moves pressed during an animation are buffered (FIFO, `maxBufferedMoves` default 8) instead of ignored**, and the next move starts as soon as the slide ends — the merge pulse continues in parallel and never blocks input. Outside Play Mode (EditMode tests) visuals update instantly. This whole queue is itself gated by the wave lock above: nothing gets buffered while a wave is running.
- All the design knobs live in `BoardManager`'s **Visuales** header: `cellSize`/`cellThickness`, `cellMesh` + `cellMaterial` (the grid tile, Procedural mode only) and `towerLevelModels` (one model per level: `[0]` = level 1, `[1]` = level 2, …; the last entry is reused for higher levels). They are `public`, so they are drag & drop in the Inspector.
- Swapping `cellMesh` never changes the board size: `BoardManager.CreateCell` scales any mesh to the cell box (`cellSize * 0.9` × `cellThickness` × `cellSize * 0.9`), recenters it by its bounds and copies those bounds into the `BoxCollider`. Keep that normalization when touching cell creation. (Anchored mode skips `CreateCell` entirely — cells already exist.)
- Tower visuals are plug-and-play: `Tower` is only the logical anchor (movement/level); `TowerVisual` owns model, scale, color, spawn growth and merge pulse. `BoardManager` calls `Tower.SetModel(...)` with the model of the level (on create, on edit-mode refresh and on merge) — `TowerVisual.SetModel` swaps the child, ignores repeated calls with the same prefab and falls back to a cube when the list is empty. `BoardManager` positions roots at the cell anchor; `TowerVisual` handles the model's height offset. Do not hand-scale or recolor tower roots; tune `baseScale`/`baseOffsetY` on `TowerVisual` instead.
- The tint per level is edited **only** in `BoardManager` → **Colores de las torres** (`useLevelColors` + `towerLevelColors`, same `[0]` = level 1 convention). `TowerVisual` does not serialize a palette: `BoardManager.ApplyTowerColors` pushes it with `SetLevelColors(...)` on create/refresh, and the tower falls back to `DefaultPalette()` only if used without a board. Do not re-add a palette field to `TowerVisual` — a per-tower copy that the board silently overwrites is what confused the designer before. `useLevelColors` off clears the property block, so the model's own material shows.
- `TowerVisual.modelBaseScale` (the model's imported scale) is captured **once** and serialized — it must never be re-derived from the already-scaled `Visual` child, or towers shrink every time Play Mode starts. `SetModel` re-captures it from the freshly instantiated prefab; for a model swapped by hand, right-click the `TowerVisual` and use *Restablecer escala base del modelo* (or rebuild the board view).

## Code style
- Comments in **Spanish**, always single-line with `//`. Never use `/// <summary>` XML docs.
- Write code readable by junior developers: descriptive names, short methods, obvious flow, no fancy patterns.
- **No namespaces** anywhere (not everyone on the team wraps their scripts, so the project stays on the global namespace). Exception: `Assets/_Custom/UI/Scripts/*` (`Custom.UI`) predates this rule and was left as-is — don't strip it without being asked, and don't add a namespace to any *new* script regardless of folder.
- **No `#if UNITY_EDITOR` and no `using UnityEditor` in runtime scripts.** Everything editor-only lives in `Assets/_Custom/Scripts/Editor/` (e.g. `BoardManagerEditor` marks the scene dirty after rebuilding). Runtime code that must work in the editor uses `ExecuteAlways` + `Application.isPlaying`.
- Fields the designer tweaks are plain `public` fields with a `//` comment and grouped under a `[Header(...)]`; `[SerializeField] private` stays only for wiring that is not meant to be touched.
- Tests live in `Assets/_Custom/Tests/Editor/` (no asmdef needed for EditMode); in tests, build boards from readable strings (e.g. `"1,1,0,0|0,0,0,0|..."`) instead of `int[,]` literals — same readability, no compiler quirks.

## Unity/MCP gotchas (verified)
- `execute_code` compiles with CodeDom (C# 6) which **mangles multi-dimensional array literals** (it transposes `int[,] { { ... } }` initializers). In snippets, build arrays programmatically (cell by cell); never trust a snippet that passes `int[,]` literals.
- After creating scripts, wait for compilation + domain reload to finish before running `run_tests`: running too early fails initialization or returns stale results (the editor may still be running the previous assembly). If test results contradict the source on disk, force a clean recompile (refresh with compile request) and re-verify.
- If compiled behavior differs from the `.cs` on disk, inspect the compiled assembly before touching the logic: fixture literal data ends up in `<PrivateImplementationDetails>` static fields and member calls can be resolved via `Module.ResolveMethod`/`ResolveField` on the IL tokens.
- `execute_code` runs the snippet as a raw method body, not a full source file — no `class`/`namespace` wrapper, no local functions, no inline `using` directives (fully-qualify types instead, e.g. `UnityEngine.Object.FindFirstObjectByType<T>()`, `UnityEditor.AssetDatabase.LoadAssetAtPath<T>(...)`). Switch `compiler: "roslyn"` only if the snippet genuinely needs C# 9+ features.
- Screenshot round-trips are slow relative to short-lived VFX (a 0.4-1s effect is usually long over by the time `manage_camera screenshot` returns). To actually see it: either temporarily lengthen the effect's duration/lifetime field **on the spawned instance** you already have a reference to (never on the shared prefab asset — see below) before screenshotting, or crop the resulting PNG down with `Texture2D.LoadImage`/`GetPixels`/`EncodeToPNG` in a follow-up `execute_code` call and `Read` the crop — a full 1920x1080 screenshot renders too small in chat to check small UI/VFX detail.
- Play Mode reverts field edits made on **scene** objects when you exit, but edits written to a loaded **prefab asset** reference (`AssetDatabase.LoadAssetAtPath`) via `SerializedObject` + `ApplyModifiedProperties`/`SetDirty` are real asset writes that can persist to disk. Don't mutate a shared prefab asset's fields just to widen a test window — instantiate a scene copy (or use the object `.Spawn()`/`Instantiate()` already handed you) and mutate that instead.
